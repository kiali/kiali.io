## Repository Overview

kiali.io is a [Hugo](https://gohugo.io) site using the [Docsy](https://www.docsy.dev/) theme (**v0.18** as a [Hugo Module](https://gohugo.io/hugo-modules/), not a git submodule). All English content lives under `content/en/`. Static assets (images, downloadable files) live under `static/`.

| Path | Purpose |
|------|---------|
| `content/en/docs/` | Main documentation pages |
| `content/en/news/` | Release notes and news |
| `static/images/documentation/` | Documentation screenshots and diagrams |
| `go.mod` / `go.sum` | Docsy theme module pin (`github.com/docsy/docsy/theme`) |
| `packages/hugoautogen/` | npm workspace generated by `hugo mod npm pack` (Bootstrap, Font Awesome) |
| `Makefile` | Local Hugo server and CRD doc generation |
| `config.toml` | Hugo site configuration |
| `package.json` | Pinned `hugo-extended` and `sass-embedded` (Docsy toolchain); run Hugo via npm scripts |

## Branch Strategy

- **`staging`** — default branch for new documentation; merged PRs here appear on the staging site.
- **`current`** — snapshot taken on each Kiali release; receives backports when needed.
- **Version branches** (e.g. `v2.32`) — frozen docs for older Kiali releases.

Target **`staging`** for new work unless backporting to `current` or a version branch.

## Local Development

```bash
# Run Hugo locally (Podman default; use DORP=docker if needed)
make serve

# Validate the site (CI)
make validate-site

# Regenerate CRD reference pages (see below)
make gen-crd-doc
```

Preview at [http://localhost:1313](http://localhost:1313). Hugo **extended** is pinned in `package.json` (`hugo-extended`); Dart Sass comes from `sass-embedded`. Invoke Hugo through npm (`npm run serve`, `npm run build:production`), not a system `hugo` binary. `npm run serve` uses `--poll 1s` and `--noHTTPCache` so SCSS edits are picked up through the `make serve` container mount and browsers do not cache `/scss/main.css` in dev. Restart the server after changing `package.json`, `config.toml`, or module mounts. After changing the Docsy module version, run `npm run update:docsy:pack` (or `npm run _prepare:modules`) and commit updates under `packages/hugoautogen/` and `go.sum`.

First-time setup: `npm run install:safe`, then `npm run approve:hugo` if you want to pre-download the Hugo binary (Netlify relies on hugo-extended self-install on first `hugo` invocation). If Hugo hangs at “Start building sites …”, check `readlink node_modules/.bin/sass` (should be under `sass-embedded`); `install:safe` / `update:docsy:pack` run `scripts/fix-sass-bin.mjs` when npm hoists the pure-JS `sass` package.

Local `make serve` / `make validate-site` use the `kiali/hugo` container image (`Dockerfile`) for Ruby/htmlproofer and mount the repo; Hugo and Sass install from npm inside the container (Node **24** / npm **≥11.16**, matching `package.json` engines). `make build-hugo` rebuilds when the image is missing or `Dockerfile` is newer than the image; use `make -e FORCE_BUILD=true build-hugo` to rebuild anyway.

## Content Layout

- Use Hugo front matter (`title`, `description`, optional `weight`) on every page.
- **Cross-link docs** with Hugo **`relref`** so broken targets fail at `hugo` build time (`refLinksErrorLevel` defaults to `ERROR`). Use paths **relative to the current page**, not absolute `/docs/...` in `ref`/`relref` (those break easily on Hugo 0.168+). Examples: `[Appearance]({{< relref "./appearance" >}})` (same section), `[RBAC]({{< relref "../Configuration/rbac" >}})`, `[anonymous setup]({{< relref "authentication/anonymous/#set-up" >}})` from `Configuration/_index.md`. For **section landing pages** (`_index.md`), use root-relative Markdown: `[Configuration](/docs/configuration/)` (Hugo does not resolve `relref` to section indexes reliably). Unresolved `relref`/`ref` fail the build; `make validate-site` (htmlproofer) still checks rendered HTML and external URLs.
- Do not add `draft = true` to pages intended for Netlify PR previews.
- Match the tone and structure of surrounding pages in the same section.

## Feature Page Screenshots

Store screenshots for **Features** pages in a subfolder named after the markdown file (without `.md`).

### Convention

| Feature page | Image directory | Markdown image path |
|--------------|-----------------|---------------------|
| `content/en/docs/Features/appearance.md` | `static/images/documentation/features/appearance/` | `/images/documentation/features/appearance/...` |
| `content/en/docs/Features/internationalization.md` | `static/images/documentation/features/internationalization/` | `/images/documentation/features/internationalization/...` |
| `content/en/docs/Features/ambient.md` | `static/images/documentation/features/ambient/` | `/images/documentation/features/ambient/...` |

### Rules

1. **New or updated feature pages** — put all new screenshots in `static/images/documentation/features/<page-name>/`.
2. **Editing a legacy feature page** — when you touch a page that still uses flat files in `features/`, move its images into `<page-name>/` in the same PR and update markdown paths.
3. **Naming** — use descriptive kebab-case filenames (e.g. `appearance-light.png`, `preferences-user-dropdown.png`). A page prefix in the filename is optional when the folder already identifies the feature.
4. **Shared images** — if one screenshot is used by multiple pages, prefer a `static/images/documentation/features/shared/` folder (create when needed) or keep a single canonical copy in the primary page's folder and link from other pages.
5. **Other doc sections** — follow existing section layout (e.g. `static/images/documentation/ossmc/` for OSSMC docs, `static/images/documentation/contribution/` for contribution guides).

Example markdown reference:

```markdown
![Light color scheme](/images/documentation/features/appearance/appearance-light.png "Light color scheme")
```

## CRD Reference Documentation

The Kiali and OSSMConsole CRD reference pages are **generated**, not hand-edited:

- `content/en/docs/Configuration/kialis.kiali.io.md`
- `content/en/docs/Configuration/ossmconsoles.kiali.io.md`

After CRD schema changes merge in [kiali/kiali-operator](https://github.com/kiali/kiali-operator), regenerate locally:

```bash
make gen-crd-doc
```

Commit the generated diff in the same PR that depends on the operator change, or in a follow-up PR once the operator CRD is on `master`.

Requires Podman or Docker (see `DORP` in the Makefile).

## Kiali MCP tool catalog

The tool tables inside `content/en/docs/AI/kiali-mcp.md` (between the `KIALI-MCP-TOOLS` markers) are generated from the Kubernetes MCP Server schema. Do not edit that block by hand. Refresh it with:

```bash
make gen-kiali-mcp-doc
```

The release script runs this on `staging` before promoting that branch, and commits the page only when the upstream schema changed. CI does not refetch the schema: a live check would fail unrelated pull requests whenever Kubernetes MCP Server changes.

## Pull Requests

1. Branch from `staging`.
2. Open a PR against `kiali/kiali.io` **`staging`**.
3. Use the Netlify deploy preview (**Details** on the PR) to verify pages and images.
4. For doc-only changes, a concise summary and a short test plan (pages to review) are enough.

Human-oriented contribution steps: [How to Contribute](content/en/docs/Contribution-guidelines/how-to-contribute.md).
